# 設計スコープのルール

## 1. 現在の設計段階

現在は、Phase 1（回答を集める）の利用体験を確定し、中核ドメインの構想を整理する段階です。設計順序と各stepの進捗は[ドメイン設計](../../docs/domain-design.md)を正とします。

作業対象:

- Account、Brain、Sourceの責務・境界とドメイン間の関係
- Phase 1の対応チャネルと入力形式、チャネルの役割分担
- Phase 1のログイン手段と復旧方針
- Phase 1のQuestion、Survey、SurveyResponseの集約、状態、不変条件、Account / Sourceとの関係
- Brain内部情報の大分類と、分類とは別に持つ共通属性
- Source Recordの粒度とkind、Brain Itemの由来（Evidence / Derivation）
- Source RecordとBrain Itemを結ぶ根拠・反証・改訂のエッジの種類と属性、その外部への開示粒度
- Source Recordの不変性、訂正・削除・撤回とBrain Itemへの波及、エクスポート範囲
- Topic LabelとAccess Labelによる用途分離、取り込み時と導出時の既定ラベル
- MCP提供時の高レベルなアクセス原則
- MVPと設計順序

## 2. 明示的な依頼なしに深掘りしないこと

- Confidenceの具体的な算出方法、閾値、提示のタイミングとUI
- 反証を検出する処理の入出力
- 外部連携時のAccess Label既定値の詳細と、Source Connectorの具体的なモデル
- 質問内容からAccess Labelの初期候補を決める方法（Phase 2）
- AI推定結果と根拠の具体的なモデル
- MCP接続クライアント、Scope、監査レコードの具体的なモデル
- データベース、テーブル、コレクション、インデックス
- API、MCPツール、イベントの具体的なスキーマ
- LINEログイン以外のログイン手段で利用する認証・認可製品の選定
- Workers AI上で利用する具体的なモデル、Embeddingの次元、インデックス構成

これらは存在しないものとして扱うのではなく、後続設計へ意図的に延期します。

## 3. 設計時の判断

- ユーザーが求めた抽象度を越えない
- 候補を確定案として記載しない
- 実装詳細でドメインの責務を決めない
- 新しい概念を追加する前に、既存の分類や責務で表現できないか確認する
- 詳細化が必要な場合は、所有するSSoTを先に決める
- 設計内容を複数文書へ展開せず、[ドキュメント運用ルール](documentation.md)に従う
